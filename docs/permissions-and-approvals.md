# Permissions and approvals

**Final-version update:** the persistent action registry now includes registered GitHub/MCP reads and dedicated synthetic Gmail reads as well as simulated email. Chief of Staff may select permitted GitHub/MCP reads; owner approval is still checked. Expiry of an unexecuted linked action fails its task and skips dependents; restart reconciliation handles stranded transitions. Earlier registry descriptions below document its initial version. See [final architecture](architecture.md).

Module G adds a server-side, persistent action authorization layer. It is separate from task approval: approving an execution task only allows that task into the scheduler and never approves a tool action. The Skills Manager remains a local deterministic execution path and does not request external-action permission.

Agents have three levels. **Ask First** creates a pending request for supported external writes. **Controlled Access** permits only configured operation IDs and destination scopes, within an owner-configured daily limit; anything outside that scope requests approval. **Full Access** can skip a repeat prompt only for a supported, validated operation. All levels fail closed for unknown operations, invalid input, and prohibited actions. The owner can edit Controlled Access operation IDs, destination domains, and daily limit in the bot form; generated agent instructions cannot change this policy.

The current supported action registry contains one deliberately simulated adapter: `simulated.email.send`. Its validated payload has `destination`, `subject`, and `body`. A preview identifies the destination and content and explicitly says no email has been sent. This is not Gmail, Composio, MCP, or a live email integration.

Requests are stored in `action_requests`; append-only lifecycle events are stored in `action_audit_log`. Lifecycle states are pending, approved, rejected, executing, succeeded, failed, cancelled, and expired. The owner can use the **Approvals** sidebar page to filter records, inspect a redacted preview, approve/reject/cancel, and execute a separately approved simulated action. Each card includes the stored invocation count (rejected/cancelled actions remain `0`) and a persisted timeline of proposal, decision, execution attempt, and completion/failure. Atomic status transitions make duplicate execution fail safely. Permissions and Controlled Access scope are checked again immediately before execution, so a later revocation or policy narrowing blocks an approved request.

API endpoints are same-origin application routes: `GET/POST /api/actions`, `GET/POST /api/actions/:id`. There is no agent endpoint to edit or delete audit logs. Credentials and secret-like fields are redacted before persistence. The external action adapter is intentionally simulated and records a result stating that no external service was contacted.

Manual demonstration: create an Ask First agent, POST a simulated email proposal through the application, then open **Approvals**. Reject it and verify it never receives an invocation result. Create a second request, approve it, select **Execute simulated action**, and verify one simulated success plus the event history. Existing persistent execution tasks continue to expose only their read-only tool allowlist; MCP/Composio writes are not enabled by this module.

Persistent execution tasks can now use only `github.public.read` and `mcp.read.invoke`, selected explicitly in the run builder. One action request is linked to one task; rejected actions make zero provider calls, and successful results become dependency output. Conversation-level Mastra approvals remain the existing provider workflow. Connected-app/MCP writes and browser-write categories remain unavailable even for Full Access. Real browser, Composio, repository, shell, filesystem and email writes have no execution adapter. Gmail retains its dedicated synthetic-message approval path and is not autonomous execution-task input. No actual email is sent and interrupted external actions are never replayed.
